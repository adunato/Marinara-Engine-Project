# CR044 — Character Briefing

_Status: Approved HLD_

## 1. Purpose

Introduce a character-owned Character Briefing: an editable, agent-maintained context document that captures higher-order, evolving story understanding such as relationships, current concerns, emotional/mental state, ongoing situations, and important developments.

The Character Briefing is additive to existing Marinara Conversation context generation. Existing mandatory and optional Conversation context behaviour remains unchanged; the latest Character Briefing is injected as an additional context source for the responding character.

## 2. V1 Scope

V1 provides:

- one Character Briefing configuration per character;
- manual briefing generation only;
- user selection of the connection used for Character Briefing generation, following the existing character-scoped connection pattern used by CR042 Character Daily Memories;
- an editor for the briefing Source Template;
- storage and display of the Latest Briefing;
- self-replacing `[[...]]` agent instruction slots inside the Source Template;
- stable ID-backed `$` entity references with autocomplete for Characters and Lorebooks inside `[[...]]` instructions;
- deterministic host-side resolution of the owning Character Card and any Character/Lorebook `$` references required by the current instruction;
- one agentic evidence tool, `search_character_daily_memories(query)`, implemented through Marinara's standard agent-tool architecture and backed by CR042 retrieval logic;
- Conversation-time injection of the Latest Briefing as an additional context block.

V1 does not provide scheduled generation, briefing-history/version browsing, deterministic briefing macros, rich-text entity chips, Character/Lorebook discovery by the agent, or general-purpose tool access.

## 3. Design Principles

### 3.1 Preserve existing Conversation behaviour

The feature must build on top of current Marinara behaviour rather than replace or suppress existing context assembly. Character Card, Persona, Conversation history/summaries, live Conversation context, and currently configured optional sources continue to be assembled normally.

The Character Briefing is deliberately additive even where limited semantic overlap exists. This minimises fork-specific prompt-pipeline divergence and reduces ongoing maintenance cost against upstream.

### 3.2 Character-owned, not chat-owned

The briefing belongs to a Character and must be generated independently of any particular Conversation. A character may participate in multiple chats and those chats may use different Personas, so briefing generation must operate at Character level rather than from an already-assembled chat prompt.

There is therefore no authoritative Persona Card for Character Briefing generation in V1. Persona context is not automatically supplied to the briefing agent.

### 3.3 Deterministic entity context, agentic memory retrieval

V1 deliberately separates deterministic application context from genuinely agentic retrieval.

Character Cards and Lorebooks are deterministic application entities. When the user explicitly references one through an ID-backed `$` token in the current instruction, Marinara resolves the exact entity before model execution and supplies its complete content directly in the agent's initial context. The agent does not search for, guess, or disambiguate Characters or Lorebooks itself.

Character Daily Memories are different: they form a potentially large Character-owned evidence corpus in which relevance depends on the instruction being executed. The agent may therefore formulate semantic searches against that corpus using the single V1 tool `search_character_daily_memories(query)`.

Natural-language names discovered in memories remain natural-language evidence. For example, if a memory mentions “Sarah” but the current instruction does not contain an ID-backed `$Sarah` reference, the agent may use the memory but must not attempt to infer which stored Character Card “Sarah” represents.

### 3.4 User-controlled structure

The user owns the briefing structure. V1 must not impose a fixed schema for Relationships, Concerns, Current Situation, or similar sections. The user may write arbitrary Markdown-style text and instructions.

### 3.5 Host-controlled document transformation

The briefing agent must not rewrite the Source Template as a whole. The host application owns parsing, replacement boundaries, and reconstruction of the generated briefing.

Only explicitly identified agent-instruction spans may be replaced by agent-produced content. Text outside those spans must be preserved by the host rather than regenerated by the model.

### 3.6 Standard tool architecture, narrow allowlist

Character Briefing has specialised orchestration, but it must not introduce a parallel tool-calling architecture.

The single V1 tool must be implemented and executed through the same standard Marinara built-in tool registry/executor used by regular agents. The Character Briefing runtime supplies a hardcoded server-side allowlist containing only `search_character_daily_memories`.

Adding a future tool to Character Briefing must be an explicit code/configuration decision. The briefing agent must not automatically inherit new standard tools, user-defined custom tools, or the complete tool set available to other agents.

## 4. Briefing Document Model and Syntax

The Character Briefing has two persisted views:

1. **Source Template** — editable by the user and retains the original Markdown, entity references, and `[[...]]` instructions for future runs.
2. **Latest Briefing** — generated from the Source Template by replacing each agent instruction slot with its generated result.

Generation must not destroy or overwrite the Source Template.

Ordinary Markdown/text is inert in V1. `[[...]]` is the only executable briefing syntax.

### 4.1 Self-replacing agent instructions — `[[...]]`

`[[...]]` defines an agent-generated replacement slot.

Example Source Template:

```markdown
# Relationships

## Amy
[[Review my current relationship with $Amy and summarise the important recent developments, current dynamic, and unresolved issues.]]

# Current concerns
[[Review relevant recent memories and summarise the concerns currently occupying my attention.]]
```

For generation, the engine must:

1. snapshot the persisted Source Template;
2. parse it and identify the exact character ranges belonging to each complete `[[...]]` instruction, including the opening and closing brackets;
3. preflight the owning Character and all explicit ID-backed references;
4. execute each instruction as a bounded agent task using the deterministic context and single allowed memory-search tool defined in Section 5;
5. obtain only the replacement content for that instruction;
6. replace exactly that `[[...]]` span in the generated copy of the document;
7. preserve all text outside identified instruction spans unchanged by the agent;
8. repeat this for every instruction slot included in the run;
9. persist the fully reconstructed document as the new Latest Briefing only after successful completion and a final Source Template snapshot check.

The source instruction remains unchanged in the editable Source Template, so a later manual generation can execute it again against newer evidence.

The model must not be asked to return a rewritten copy of the complete Markdown document. The host must use a constrained result or equivalent deterministic protocol that associates one generated result with one instruction slot.

Agent output for a slot must contain the requested briefing content only. It must not add explanations about the generation process, restate the instruction, emit headings or wrappers not requested by the instruction, or modify neighbouring Markdown.

V1 executes instruction slots sequentially as separate bounded agent sessions. Every slot sees the same Source Template snapshot; generated output from an earlier slot is not silently substituted into the template context seen by a later slot.

If generation fails before a complete valid result is assembled, the previously persisted Latest Briefing must remain intact rather than being replaced with a partial document.

### 4.2 Entity references — `$...` inside instructions

The `$` reference mechanism exists to let an instruction point unambiguously at a Marinara Character or Lorebook.

`$` has special behaviour only while the caret is inside a `[[...]]` instruction. Outside an instruction it is ordinary text and must not trigger entity lookup.

When the user types `$` inside an instruction, the editor opens an autocomplete picker adjacent to the caret. The picker initially supports:

- **Characters**;
- **Lorebooks**.

The picker must:

- search/filter as the user continues typing after `$`;
- clearly distinguish Character results from Lorebook results;
- allow keyboard navigation and selection;
- allow mouse/touch selection;
- disambiguate duplicate display names using available secondary metadata such as Character avatar/details or Lorebook category/description;
- insert a readable persistent reference backed by the selected entity's stable ID.

A conceptual persisted form is:

```text
$[character:<id>|Amy]
$[lorebook:<id>|Asteria]
```

The exact serialization/escaping rules are an implementation detail finalised in the LLD. Stable entity type and ID are authoritative; display labels exist for readability only.

At generation time, explicit `$` references are resolved by stable ID. The runtime must never fall back to guessing by display name.

For a given instruction slot, only `$` references occurring inside that instruction are expanded into full entity data in the slot's initial model context. References elsewhere in the Source Template remain visible as readable template text but are not automatically expanded for that slot.

If a referenced entity has been deleted or is otherwise unresolved, generation fails clearly before model execution and retains the existing Latest Briefing.

V1 does not require rich chip/pill rendering. A normal text editor with autocomplete and readable ID-backed tokens is sufficient.

### 4.3 Deterministic `{{...}}` macros

Deterministic briefing macros are out of scope for V1.

They were part of an earlier design in which Character Briefing was expected to replace more of the normal Conversation prompt. Because CR044 now deliberately retains Marinara's normal Conversation context and adds the briefing on top, the V1 feature does not need a second deterministic prompt-assembly language.

A future CR may add briefing-specific macros if a concrete use case emerges.

## 5. Character Briefing Agent

### 5.1 Execution model

Briefing generation is an explicit manual action initiated by the user from the Character Briefing UI.

The selected Character Briefing generation connection is resolved once at the start of the run and is used for every instruction slot in that run. Connection selection is Character Briefing configuration and is independent of both CR042's Daily Memory formation connection and any connection configured on a Conversation.

The agent's purpose is to produce replacement briefing content, not a conversational reply as the character and not a rewritten complete briefing document.

V1 runs each instruction slot sequentially in its own bounded tool-capable model session. The host retains responsibility for slot identity, source offsets, output validation, reconstruction, and atomic publication.

### 5.2 Exact initial context for every instruction slot

The host constructs the initial context explicitly. The model is not expected to discover its foundational context through tools.

Every slot receives the following inputs.

#### A. Owning Character Card

The complete canonical Character Card for the Character whose Briefing is being generated is always supplied directly.

This establishes whose perspective, relationships, concerns and situation the Briefing describes. First-person terms such as “my” in an instruction refer to this owning Character unless the instruction explicitly states otherwise.

The owning Character Card does not require a tool call.

#### B. No Persona Card

No Persona Card is supplied automatically in V1.

The Briefing is Character-owned across potentially multiple Conversations, and those Conversations may use different Personas. There is therefore no single Persona that can be treated as authoritative Character-level context.

#### C. Complete Source Template snapshot

The complete Source Template snapshot used for the run is supplied unchanged for contextual orientation.

It lets the agent understand:

- the overall purpose and structure of the Briefing;
- the section in which the current instruction appears;
- what other sections are intended to cover;
- the user's wording and organisation of the document.

The Source Template is explicitly marked read-only/contextual. The agent must not rewrite or complete it as a whole.

Every slot sees the same source snapshot, not a partially reconstructed version containing outputs produced for earlier slots.

#### D. Current instruction

The exact current `[[...]]` instruction is identified separately from the Source Template.

The model receives the instruction text without the enclosing brackets and an explicit contract that it must produce content for this slot only.

#### E. Resolved entity data for the current instruction

Only ID-backed `$` references contained within the **current instruction** are expanded into application data for that slot.

For each referenced Character, the host supplies the complete canonical Character Card identified by the stored Character ID.

For each referenced Lorebook, the host supplies the complete Lorebook identified by the stored Lorebook ID, including its entries/content as represented by the canonical Lorebook resource.

The agent is not given a Character/Lorebook discovery mechanism. Natural-language names in the instruction, Source Template, or retrieved memories do not grant access to application entities.

#### F. Current date/time

The host supplies current date/time information so terms such as “currently”, “recently”, or “over the last few days” have an explicit temporal reference.

#### G. Tool definition

The only V1 agent tool is `search_character_daily_memories(query)` as defined below.

### 5.3 Character Daily Memory tool

The model-facing contract is deliberately minimal:

```text
search_character_daily_memories(query)
```

The tool:

- is implicitly scoped by the host to the owning Character; `characterId` is not a model-supplied argument;
- searches only the active CR042 Character Daily Memory corpus for that Character;
- uses the same central CR042 relevance/ranking/filtering/result-selection policy used for normal Conversation Daily Memory retrieval;
- accepts no date filters, result limit, ranking weights, or other retrieval-tuning parameters from the agent;
- returns the selected memory records with the evidence/provenance fields that the existing CR042 retrieval path makes available and that are useful to the model.

The agent may issue more than one semantic query within the bounded tool-round budget when the instruction benefits from iterative investigation.

Central retrieval is a mandatory implementation prerequisite, not an assumption about staging. Before the Character Briefing tool is registered as usable, implementation must expose the CR042 Conversation retrieval/ranking/filtering/result-selection policy through one reusable server-side boundary. Both Conversation Daily Memory injection and this tool must call that boundary; CR044 must not copy or approximate the ranking algorithm. A fixture with known scores/order must prove that the tool receives the same selected, ranked records that Conversation injection receives.

If the shared retrieval boundary or its required embedding/vector backend is unavailable, the tool must return the normal structured retrieval-unavailable/error result and the current slot must follow the standard tool-failure path. It must never silently substitute an unranked query, a second ranking policy, or unconstrained raw memories. Conversation retrieval continues to use the existing CR042 safe-degradation policy when that policy applies.

### 5.4 Tool boundaries

The hardcoded V1 Character Briefing allowlist contains exactly:

```text
search_character_daily_memories
```

The briefing agent does **not** receive:

- Character search/get tools;
- Lorebook search/get tools;
- chat/history enumeration tools;
- Professor Mari `app_data`;
- web search;
- mutation tools;
- custom user tools;
- filesystem/shell tools;
- game, Spotify, or other unrelated built-in tools.

Character/Lorebook evidence is pre-resolved deterministic context rather than agentic tool access.

## 6. Character Card UI

### 6.1 Location

Character Briefing is exposed as a dedicated tab in the existing Character Card UI.

The feature should feel like character metadata/context management, not a chat-level setting.

### 6.2 V1 layout

The tab contains three logical areas plus the manual generation action.

#### Source Template Editor

An editable Markdown-style text area containing the user's briefing structure, self-replacing agent instructions, and ID-backed entity references.

Required editor behaviours:

- ordinary text/Markdown editing;
- `[[...]]` instruction syntax as plain text;
- `$` autocomplete only when the caret is inside an instruction;
- autocomplete results grouped or otherwise clearly differentiated between Characters and Lorebooks;
- continued typing after `$` filters the picker;
- duplicate-name results are visibly disambiguated before selection;
- selection inserts an ID-backed persistent reference;
- keyboard, mouse, and touch selection are supported;
- normal keyboard editing remains possible without requiring a rich-text editor.

The editor always displays the persistent source form, including `[[...]]` instructions. Generated replacement text does not overwrite the source editor.

#### Generation connection

The tab provides a Character Briefing generation connection selector following the existing tab-local Character Daily Memories connection-selection convention. Reuse an already shared primitive only if one exists; creating a new cross-tab selector component is outside CR044 scope.

The setting belongs to Character Briefing and is persisted independently from CR042 settings and Conversation settings.

Resolution follows the character-scoped agent pattern: use the explicitly configured Character Briefing connection when present; when unset, use the normal default agent connection/fallback infrastructure. It must never inherit an arbitrary source Conversation's chat connection.

If a configured connection reference is invalid/deleted and cannot be resolved according to the standard connection fallback rules, generation fails clearly without altering Latest Briefing.

#### Latest Briefing

A read-only presentation of the most recently generated Character Briefing.

This is the transformed result in which `[[...]]` instructions have been replaced by their generated content. It is the briefing supplied to Conversation generation.

The latest result should be clearly separated from the Source Template so the user can distinguish:

- the persistent instructions and structure that define what should be generated; and
- the current generated briefing produced from those instructions.

V1 stores/displays only the latest generated briefing. A historical list of all previous briefing generations is out of scope.

### 6.3 Manual generation action

The tab provides a clear action such as **Generate Briefing** / **Update Briefing**.

On invocation:

1. the current Source Template and generation-connection setting are persisted;
2. the selected/default Character Briefing generation connection is resolved once for the run;
3. the engine snapshots and parses all `[[...]]` replacement slots;
4. the owning Character Card and all explicit `$` references are preflighted by stable ID;
5. for each slot, the host constructs the exact initial context defined in Section 5.2;
6. the Character Briefing agent may retrieve relevant Daily Memories through `search_character_daily_memories(query)`;
7. the host reconstructs a generated copy by replacing only the identified instruction spans with their corresponding outputs;
8. the complete generated document becomes the new Latest Briefing only after full success and a final source-snapshot check;
9. the Source Template remains unchanged.

The existing Latest Briefing remains available if generation fails.

### 6.4 Empty state

For a character with no generated briefing yet, the tab should show:

- the Source Template editor;
- the generation connection selector;
- the manual generation action;
- a simple empty state in the Latest Briefing area explaining that no briefing has yet been generated.

## 7. Conversation Integration

When a Conversation response is generated for a character with a non-empty Latest Briefing:

1. Marinara assembles the normal Conversation context using existing behaviour;
2. the Latest Briefing for the responding character is added as a distinct context block;
3. the normal generation flow continues unchanged.

The feature must not suppress or replace existing Character Card, Persona, summary/history, status/context, memory, lorebook, awareness, or other optional prompt sources.

For group Conversations, briefing injection must be character-specific: only the briefing(s) for the resolved responding character target or targets should be exposed according to the existing response-target/visibility model. A group member that is not a current response target contributes no briefing. If multiple characters are valid response targets, add one clearly attributed block per target in the existing target order, with duplicate Character IDs emitted once; do not merge or leak one character's briefing into another character's context.

Architecturally, the existing generation route remains the owner of response-target and visibility resolution and of the `AgentContext` assembled for the final model request. After those targets are resolved, the Character Briefing formatter appends the applicable read-only blocks at that existing context boundary, immediately before the final provider request. This additive seam must leave every existing context source unchanged.

## 8. Persistence

V1 requires persisted character-level state for at least:

- Source Template text;
- Character Briefing generation connection ID, nullable when the normal default agent connection should be used;
- Latest Briefing text;
- latest successful generation timestamp/status as needed by the UI;
- any metadata required to preserve/resolve ID-backed entity references if that metadata is not fully encoded in the stored text.

The data belongs to the Character rather than to individual chats.

No historical briefing archive is required in V1.

The persistence implementation must register the new record in every file-backed persistence layer used by staging: the schema/table definition and export/barrel, the file-backed store's key/index/serializer registration, and any format/version migration or compatibility registry. The record has a required Character relationship/key and a unique one-row-per-Character invariant; `generationConnectionId` is an optional connection reference handled by the repository's existing reference policy. Reads of files created before CR044 must produce the default empty state without backfill, and writes must use the existing atomic file/transaction mechanism.

Character deletion must remove the associated briefing in the same deletion boundary (or the repository's equivalent cascade hook), and connection deletion must follow the established optional-reference cleanup policy. No orphaned briefing row or dangling required Character relationship may remain. Configuration saves and Latest Briefing publication must each preserve the existing data on failure, and publication must update `latestBriefing` and its timestamp atomically.

## 9. Explicitly Out of Scope for V1

- deterministic `{{...}}` briefing macros;
- scheduled or automatic briefing generation;
- startup catch-up scheduling;
- briefing generation triggered automatically by Conversation activity;
- history/version browser for prior generated briefings;
- rich-text entity chips as a requirement;
- Character/Lorebook agent discovery or name guessing;
- Character/Lorebook get/search tools for the briefing agent;
- unrestricted/general application-data access for the briefing agent;
- user-configurable Character Briefing tool selection;
- redesign of CR042 Daily Memory formation;
- separate CR044 Daily Memory ranking/search logic;
- replacement or suppression of existing Conversation context sources;
- fixed system-defined briefing sections/schema;
- chat-specific Character Briefings;
- Persona selection/injection for Character Briefing generation.

## 10. Reuse / Implementation Direction

Implementation planning should prefer existing Marinara primitives wherever possible:

- canonical Character Card and Lorebook storage/services for deterministic host-side reference resolution;
- existing Conversation `@mention`/completion interaction as a UI precedent for entity autocomplete;
- CR042's character-owned Daily Memory store and the same centralized retrieval/ranking/limiting policy used by Conversation injection, exposed through the mandatory shared retrieval boundary above;
- the existing tab-local Character-scoped connection-selection convention for the Briefing selector; do not expand scope to create a shared UI primitive;
- Marinara's standard built-in tool registry, `AgentToolContext`, and tool executor for `search_character_daily_memories`;
- existing prompt/context injection mechanisms for adding a new character-specific context block without altering current source behaviour;
- existing LLM provider/fallback/tracing infrastructure, including the staging Phoenix tracing path.

The intent is to add one narrow character-level capability while minimising changes to core Conversation context assembly and avoiding parallel application-data or tool architectures.

## 11. Implementation Decisions Deferred to Planning / LLD

The following do not require additional product direction unless implementation investigation exposes a material trade-off:

- exact serialized/escaping syntax for ID-backed entity references;
- exact shared/reused editor autocomplete component structure;
- exact internal extraction/refactor required to make CR042's current Conversation Daily Memory retrieval policy callable from the standard tool executor;
- exact constrained terminal-result schema used for one slot replacement;
- precise context-block formatting and insertion point for the Latest Briefing;
- persistence schema/table details for the dedicated associated briefing record;
- exact reuse of an already shared connection-selector primitive, if one exists; no new shared selector component is required or implied.

The following are **not** deferred decisions: V1 uses one bounded session per instruction, each slot receives the complete Source Template snapshot and owning Character Card, only current-instruction `$` references are expanded, no Persona is supplied, and the only agentic tool is `search_character_daily_memories(query)`.

## 12. Acceptance Summary

CR044 V1 is complete when a user can open a Character Card, select the Character Briefing tab, choose the generation connection, edit a free-form Source Template containing self-replacing `[[...]]` instructions and ID-backed `$` Character/Lorebook references inside those instructions, and manually generate a briefing.

For each instruction, Marinara must deterministically supply the owning Character Card, complete Source Template snapshot, current instruction, current date/time, and complete data for Character/Lorebook references occurring in that instruction. The model may investigate only the owning Character's CR042 Daily Memories through the standard built-in `search_character_daily_memories(query)` tool.

The generated Latest Briefing must be constructed host-side by replacing only the exact `[[...]]` instruction spans, leaving the Source Template unchanged and retaining the previous Latest Briefing on failure. The latest successful briefing must then be included as additional character-specific context during normal Conversation generation without changing existing Conversation context behaviour.
