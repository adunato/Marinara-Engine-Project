# CR044 — Character Briefing

_Status: Draft HLD_

## 1. Purpose

Introduce a character-owned Character Briefing: an editable, agent-maintained context document that captures higher-order, evolving story understanding such as relationships, current concerns, emotional/mental state, ongoing situations, and important developments.

The Character Briefing is additive to existing Marinara Conversation context generation. Existing mandatory and optional Conversation context behaviour remains unchanged; the latest Character Briefing is injected as an additional context source for the responding character.

## 2. V1 Scope

V1 provides:

- one Character Briefing configuration per character;
- manual briefing generation only;
- an editor for the briefing Source Template;
- storage and display of the Latest Briefing;
- self-replacing `[[...]]` agent instruction slots inside the Source Template;
- stable ID-backed `$` entity references inside agent instructions, with autocomplete for Characters and Lorebooks;
- read-only briefing-agent access to Character Cards, character-level Daily Memories, and Lorebooks;
- Conversation-time injection of the Latest Briefing as an additional context block.

V1 does not provide deterministic `{{...}}` briefing macros, scheduled generation, or briefing-history/version browsing.

## 3. Design Principles

### 3.1 Preserve existing Conversation behaviour

The feature must build on top of current Marinara behaviour rather than replace or suppress existing context assembly. Character Card, Persona, Conversation history/summaries, live Conversation context, and currently configured optional sources continue to be assembled normally.

The Character Briefing is deliberately additive even where limited semantic overlap exists. This minimises fork-specific prompt-pipeline divergence and reduces ongoing maintenance cost against upstream.

Because normal Conversation generation continues to provide deterministic identity, persona, history, summary, status, and other configured context, CR044 does not need a second deterministic macro system inside the briefing template for V1.

### 3.2 Character-owned, not chat-owned

The briefing belongs to a Character and must be generated independently of any particular Conversation. A character may participate in multiple chats, so briefing generation must operate against character-level evidence rather than an already-assembled chat prompt.

### 3.3 Agentic interpretation, selective retrieval

The briefing should focus on information that benefits from interpretation rather than deterministic prompt assembly: relationships, concerns, current state of mind, unresolved threads, and important story developments.

The agent should retrieve only evidence relevant to the user's briefing instructions. Large source collections must not be preloaded wholesale into every run.

### 3.4 User-controlled structure

The user owns the briefing structure. V1 must not impose a fixed schema for Relationships, Concerns, Current Situation, or similar sections. The user may write arbitrary Markdown-style text and agent instructions.

### 3.5 Host-controlled document transformation

The briefing agent must not rewrite the Source Template as a whole. The host application owns parsing, replacement boundaries, and reconstruction of the generated briefing.

Only explicitly identified `[[...]]` instruction spans may be replaced by agent-produced content. Text outside those spans must be preserved by the host rather than regenerated by the model.

## 4. Briefing Document Model and Syntax

The Character Briefing has two persisted views:

1. **Source Template** — editable by the user and retains the original Markdown, entity references, and `[[...]]` instructions for future runs.
2. **Latest Briefing** — generated from the Source Template by replacing each agent instruction slot with its generated result.

Generation must not destroy or overwrite the Source Template.

V1 intentionally has only one executable syntax: `[[...]]`.

Ordinary Markdown and ordinary text are inert. A `$` entity reference is interpreted specially only when it occurs inside a `[[...]]` instruction.

### 4.1 Self-replacing agent instructions — `[[...]]`

`[[...]]` defines an agent-generated replacement slot.

Example Source Template:

```markdown
# Relationships

## Amy
[[Review my current relationship with $Amy and summarise the important recent developments, current dynamic, and unresolved issues.]]

# Current concerns
[[Review relevant recent memories and summarise the concerns currently occupying my attention.]]
```

For generation, the engine must:

1. parse the Source Template and identify the exact character ranges belonging to each complete `[[...]]` instruction, including the opening and closing brackets;
2. resolve any ID-backed entity references contained in that instruction;
3. execute the requested agent work using the allowed evidence tools;
4. obtain only the replacement content for that instruction;
5. replace exactly that `[[...]]` span in the generated copy of the document;
6. preserve all text outside identified instruction spans unchanged by the agent;
7. repeat this for every instruction slot included in the run;
8. persist the fully reconstructed document as the new Latest Briefing only after successful completion.

The source instruction remains unchanged in the editable Source Template, so a later manual generation can execute it again against newer evidence.

The model must not be asked to return a rewritten copy of the complete Markdown document. The host should use a constrained structured result or equivalent protocol that associates one generated result with one instruction slot deterministically.

Agent output for a slot must contain the requested briefing content only. It must not add explanations about the generation process, restate the instruction, emit headings or wrappers not requested by the instruction, or modify neighbouring Markdown.

The exact orchestration protocol is left to implementation planning. Multiple instruction slots may be executed within one controlled agent session or through separate bounded calls, provided the replacement mapping remains deterministic and only the intended spans are changed.

If generation fails before a complete valid result is assembled, the previously persisted Latest Briefing must remain intact rather than being replaced with a partial document.

### 4.2 ID-backed entity references — `$...` inside `[[...]]`

Agent instructions may contain explicit references to Marinara entities. V1 supports:

- Characters;
- Lorebooks.

The purpose of a reference is deterministic identity, not textual substitution. Selecting a reference binds the instruction to the entity's stable ID so the agent never has to infer which similarly named entity the user meant.

Conceptually, a stored reference must carry at least:

- entity type;
- stable entity ID;
- a human-readable display label.

The exact serialized token format is an implementation detail for the LLD. A conceptual representation is:

```text
$[character:<id>|Amy]
$[lorebook:<id>|Asteria]
```

The runtime resolves the entity by ID. The label is for readability and must not be used as the authoritative identity.

Entity references are only executable inside a `[[...]]` instruction. A `$` typed elsewhere in ordinary Markdown remains ordinary text and must not trigger entity semantics.

If a referenced entity no longer exists, generation must surface the unresolved reference rather than silently searching by the old display name or allowing the agent to guess. The previous successful Latest Briefing remains unchanged on that failed run.

## 5. Character Briefing Agent

### 5.1 Execution model

Briefing generation is an explicit manual action initiated by the user from the Character Briefing UI.

For each instruction slot, the runtime provides the agent with the information required for that task, including:

- the owning Character ID;
- the instruction text;
- enough surrounding/template context to understand the requested output where necessary;
- current date/time where relevant;
- resolved stable entity references;
- a restricted read-only toolset.

The agent's purpose is to produce replacement briefing content, not a conversational reply as the character and not a rewritten complete briefing document.

The implementation may maintain one tool-using agent session across multiple slots when useful, but each returned replacement must remain explicitly attributable to one source instruction.

### 5.2 Initial read-only evidence tools

V1 exposes only the evidence capabilities required for the first implementation.

#### Character Cards

The agent can retrieve Character Cards by stable Character ID and can search/list characters when needed. This allows it to contextualise the owning character and explicitly referenced characters without loading every card into the initial prompt.

The implementation should reuse existing Marinara structured character data-access services where practical rather than introducing a parallel storage/retrieval path.

#### Character Daily Memories

The agent can search and read the character-level Daily Memories introduced by CR042.

CR044 does not own or modify Daily Memory formation. It consumes the character-owned memory store created by CR042 as evidence. Retrieval should support selective relevant-memory access rather than preloading the complete memory corpus.

The exact read/search API should be aligned to the final CR042 implementation during implementation planning.

#### Lorebooks

The agent can identify Lorebooks, inspect their entry index, and retrieve selected entries in full. This allows briefing instructions to ask the agent to interpret canonical world information without automatically adding complete lorebooks to every briefing run.

Existing Marinara Lorebook data-access services should be reused where practical.

### 5.3 Tool boundaries

The Character Briefing agent must not receive Professor Mari's unrestricted/general application-data interface. Its V1 tool surface is read-only and narrowly scoped to Character Cards, Character Daily Memories, and Lorebooks.

## 6. Character Card UI

### 6.1 Location

Character Briefing is exposed as a dedicated tab in the existing Character Card UI.

The feature should feel like character metadata/context management, not a chat-level setting.

### 6.2 V1 layout

The tab contains two primary areas.

#### Source Template Editor

An editable Markdown-style text area containing the user's briefing structure and self-replacing `[[...]]` instructions.

The editor always displays the persistent source form, including its `[[...]]` instructions. Generated replacement text does not overwrite the source editor.

Required base editor behaviours:

- ordinary text/Markdown editing;
- `[[...]]` instructions remain visible and directly editable as text;
- normal keyboard editing, selection, copy/paste, undo, and cursor behaviour;
- no rich-text editor is required for V1.

#### Entity-reference autocomplete

The `$` picker is contextual to an agent instruction.

Expected interaction:

1. The user places the caret inside a `[[...]]` instruction and types `$`.
2. An autocomplete popup opens at or near the caret.
3. The popup searches across V1 referenceable entity types: Characters and Lorebooks.
4. Results are grouped by type or otherwise clearly labelled as **Character** versus **Lorebook**.
5. Typing after `$` filters the results by display name.
6. The user can navigate results by keyboard and mouse/touch and select one.
7. Selection inserts one human-readable, ID-backed reference token at the caret and closes the popup.
8. The surrounding instruction remains ordinary editable text.

Typing `$` outside a `[[...]]` instruction must not open this entity picker and must behave as ordinary text.

Autocomplete results must make duplicate names distinguishable before selection. The UI should use the identifying information already available for each entity, for example:

- Character: avatar where available plus name and a secondary identifying detail;
- Lorebook: lorebook icon/type plus name and a secondary description/category where available.

The implementation plan/LLD may select the exact secondary fields based on existing APIs, but duplicate display names must not produce visually indistinguishable choices.

The inserted token does not need rich pill/chip rendering in V1. A readable text token is acceptable provided it persists the stable entity ID and remains editable/recoverable.

Examples of the authoring experience are conceptually:

```markdown
[[Describe how my relationship with $Amy has changed recently.]]

[[Review $Asteria and explain which current political facts materially affect me.]]
```

where `$Amy` and `$Asteria` are visibly readable references whose stored representation also carries their stable IDs.

#### Latest Briefing

A read-only presentation of the most recently generated Character Briefing.

This is the transformed result in which `[[...]]` instructions have been replaced by their generated content. It is the briefing supplied to Conversation generation.

The latest result should be clearly separated from the Source Template so the user can distinguish:

- the persistent instructions and structure that define what should be generated; and
- the current generated briefing produced from those instructions.

V1 stores/displays only the latest generated briefing. A historical list of all previous briefing generations is out of scope.

### 6.3 Manual generation action

The tab provides a clear action such as **Generate Briefing** / **Update Briefing**.

On invocation:

1. the current Source Template is persisted;
2. the engine parses all `[[...]]` replacement slots and validates their entity references;
3. the Character Briefing agent performs the required retrieval/reasoning using its restricted evidence tools;
4. the host reconstructs a generated copy by replacing only the identified instruction spans with their corresponding outputs;
5. the complete generated document becomes the new Latest Briefing;
6. the Source Template remains unchanged.

The existing Latest Briefing remains available if generation fails.

### 6.4 Empty state

For a character with no generated briefing yet, the tab should show:

- the Source Template editor;
- the manual generation action;
- a simple empty state in the Latest Briefing area explaining that no briefing has yet been generated.

## 7. Conversation Integration

When a Conversation response is generated for a character with a non-empty Latest Briefing:

1. Marinara assembles the normal Conversation context using existing behaviour;
2. the Latest Briefing for the responding character is added as a distinct context block;
3. the normal generation flow continues unchanged.

The feature must not suppress or replace existing Character Card, Persona, summary/history, status/context, memory, lorebook, awareness, or other optional prompt sources.

For group Conversations, briefing injection must be character-specific: only the briefing(s) appropriate to the responding character(s) should be exposed according to the existing response-target/visibility model.

## 8. Persistence

V1 requires persisted character-level state for at least:

- Source Template text;
- Latest Briefing text;
- latest generation timestamp/status as needed by the UI;
- any metadata required to preserve/resolve ID-backed entity references if that metadata is not fully encoded in the stored text.

The data belongs to the Character rather than to individual chats.

No historical briefing archive is required in V1.

## 9. Explicitly Out of Scope for V1

- deterministic `{{...}}` macros in the Character Briefing Source Template;
- scheduled or automatic briefing generation;
- startup catch-up scheduling;
- briefing generation triggered automatically by Conversation activity;
- history/version browser for prior generated briefings;
- rich-text entity chips as a requirement;
- unrestricted application-data access for the briefing agent;
- redesign of CR042 Daily Memory formation;
- replacement or suppression of existing Conversation context sources;
- fixed system-defined briefing sections/schema;
- chat-specific Character Briefings.

## 10. Reuse / Implementation Direction

Implementation planning should prefer existing Marinara primitives wherever possible:

- Character Card data access already used by Professor Mari and generation services;
- Lorebook list/index/entry retrieval already available through structured application-data services;
- existing Conversation `@mention`/completion interaction as a UI precedent for caret-aware entity autocomplete;
- CR042's final character-owned Daily Memory storage/retrieval implementation for memory evidence;
- existing prompt/context injection mechanisms for adding a new character-specific context block without altering current source behaviour.

The intent is to add one narrow character-level capability while minimising changes to core Conversation context assembly.

## 11. Implementation Decisions Deferred to Planning / LLD

The following do not require additional product direction unless implementation investigation exposes a material trade-off:

- exact serialized syntax for ID-backed entity references;
- exact shared/reused editor autocomplete component structure;
- exact secondary metadata shown to disambiguate duplicate autocomplete results;
- exact Character Daily Memory query/read interface after CR042 is finalised;
- exact structured protocol used to associate agent output with replacement slots;
- whether multiple replacement slots share one bounded agent/tool session or use separate calls;
- precise context-block formatting and insertion point for the Latest Briefing;
- persistence schema/location within the Character model versus a dedicated associated record.

These should be resolved by implementation planning/LLD based on the existing codebase and the principle of minimum divergence from upstream.

## 12. Acceptance Summary

CR044 V1 is complete when a user can open a Character Card, select the Character Briefing tab, edit a free-form Source Template containing self-replacing `[[...]]` instructions, use `$` autocomplete inside those instructions to insert stable ID-backed Character/Lorebook references, manually generate a briefing using read-only Character Card, CR042 Daily Memory, and Lorebook evidence, see the transformed Latest Briefing in the same tab, and have that Latest Briefing automatically included as additional context when Marinara generates a Conversation response for that character — without changing existing Conversation context behaviour.

Generation must preserve the Source Template and must construct the Latest Briefing by replacing only the exact `[[...]]` instruction spans with their corresponding agent outputs; the agent must not be allowed to rewrite unrelated Markdown.
